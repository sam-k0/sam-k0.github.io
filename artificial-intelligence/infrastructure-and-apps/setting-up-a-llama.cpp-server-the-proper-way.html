Setting up a llama.cpp server the proper way

As I recently got to set up multiple instances of llama.cpp and there's just so much bad advice out there (bad as in "not an easily extensible and manageable setup"), here's my guide.

The Goal

  • Having an openai-compatible api
  • easily configuring parameters for each model individually
  • loading and unloading models at runtime
  • fast inference speeds using multi token prediction (~x2 token decoding speed)

Prerequisites

The probably most important thing in this is your hardware,

Note

Also you need to have the proper host workload installed on your machine:

  • Nvidia GPUs need CUDA
  • AMD GPUs need ROCm

Check if it's installed using `rocm-smi

Also docker is required.

The model I'm gonna install is gemma 4 e4b it.

Setting up the directory structure

Firstly, I'd create a new directory llamacpp-server to put all future files in, it's gonna be the parent directory that stores configs and models.

Next, cd llamacpp-server and mkdir models. This is where we'll store the models, projectors (mmproj files), mtp heads etc. each in their own subdirectory. The directory stucture will look something like this:

llamacpp-server/
	- models.ini
	- docker-compose.yml
	- models/
		- gemma-4-e4b-it/
			- gemma-4-E4B-it-Q4_K_M.gguf
			- MTP/
				- mtp-gemma-4-E4B-it.gguf
			- mmproj-F16.gguf

Next, download the following files from huggingface:

  • gemma-4-E4B-it-Q4_K_M, the main model file, a 4 bit quantization
  • mmproj-F16.gguf, the multimodal projector: enables the model to "see" images
  • mtp-gemma-4-E4B-it.gguf, the multi token generation head

After moving them to the directories above, let's get to setting up the docker-compose file which you can create next to the models/ directory.

services:
	llama-server:
	image: ghcr.io/ggml-org/llama.cpp:server-rocm@sha256:455f35bacf8d73e03a8679d649651749a0132b3f33007d3fa92699d4dc38fa1b
	container_name: llama-server
	devices:
		- /dev/kfd:/dev/kfd
		- /dev/dri:/dev/dri
	# needed for ROCm, check your detailed setup for nvidia
	group_add:
		- video
	volumes:
		- ./models:/models:ro
		- ./models.ini:/models.ini:ro
	environment:
		LLAMA_ARG_MODELS_DIR: /models
		LLAMA_ARG_MODELS_PRESET: /models.ini
		LLAMA_ARG_MODELS_MAX: "1"
		LLAMA_ARG_MODELS_AUTOLOAD: "true"
	ports:
		- "9931:9931"
	restart: unless-stopped
	command:
		- "--host"
		- "0.0.0.0"
		- "--port"
		- "9931"

So aside from the obvious things like providing the docker image pinned to an exact version hash and naming the container llama-server, there's some special stuff happening:

The group_add is required for AMD ROCm as that's the usergroup that keeps the privilege for using the gpu. This is different for nvidia cards, so I don't think you'll need that for cuda.

The volumes block mounts the models/ directory to the container, as well as the models.ini file that I didn't go over yet but create next.

The env vars do the following:

  • LLAMA_ARG_MODELS_DIR tells llamacpp where to look for models and also checks subdirectories
  • LLAMA_ARG_MODELS_PRESET points to the mentioned models.ini file which keeps all of the model specific config
  • LLAMA_ARG_MODELS_MAX defines how many models can be loaded concurrently, if set to 1, the current model will be unloaded upon requesting to use another one. If you are rich, set this to 2 or 3.
  • LLAMA_ARG_MODELS_AUTOLOAD does what it says, it enables llamacpp to load and unload requested models during runtime.

The other settings are basic docker stuff so you already know what they do.

Configuring models in models.ini

As mentioned above, models.ini defines global settings that each model inherits but also overrides.

Create models.ini next to the models/ directory and next to the docker compose file.

First, define some general settings:

version = 1

[*]
n-gpu-layers = 999
flash-attn = on
parallel = 1
threads = 8
threads-batch = 8
ctx-size = 32768

The asterisk * configuration part defines the following, in order:
We want to offload all layers to gpu, use flash attention, handle 1 request in parallel, with 8 threads and a batchsize of 8, while having a context window size of 32768 tokens.

So unless specified differently, all models will inherit this configuration.
But for gemma 4 using MTP there's some changes needed, so below comes this block:

[gemma-4-e4b-it-mtp]
model = /models/gemma-4-E4B-it-Q4_K_M/gemma-4-E4B-it-Q4_K_M.gguf
; flash-attn MUST be off for gemma when using mtp.. thats what it says in the unsloth docs.
flash-attn = off
alias = gemma-4-e4b-it-mtp
model-draft= /models/gemma-4-E4B-it-Q4_K_M/MTP/mtp-gemma-4-E4B-it.gguf
spec-type = draft-mtp
spec-draft-n-max = 2
mmproj = /models/gemma-4-E4B-it-Q4_K_M/mmproj-F16.gguf

This section defines settings specific to gemma 4, as it points model to the gemma 4.gguf file. It also overrides the global flash-attn setting to off as this is required for mtp to work with gemma.
Next, it sets an alias name and model-draft points to the mtp-head.
spec-type sets the mtp mode and spec-draft-n-max defines how many tokens should be predicted at once. Higher numbers don't necessarily mean better results as the acceptance rate may vary.
Lastly, mmproj points to the multimodal projector so we can have our model describe images or OCR some text.

These variables mostly are also reflected by env vars and a whole list can be found here.

Running the container

So after setting up all the files, do docker compose up and see the llamacpp logs for any errors. If everything is fine, open localhost:9931 in your browser and you should see the llama-ui open.

Select gemma 4 as your model and try to load it, check the logs for any critical errors. Otherwise, the page will show a little notification that everything went well.

If there's any timeout for pulling the image

Unauthenticated downloads to the github container registry (ghcr) tend to have a strict ratelimit. If you run into problems while pulling, authenticate to the ghcr docker registry with your github account.

Result comparison on gemma 4

On my 7900 XT with above setup, I get the following results:

  • Using MTP, ~150 tps
  • Without MTP, ~110 tps

Pushing to the extreme

I have also set this up on two RTX 6000 Ada Generation cards, so thats 96 GB of VRAM (2x 48GB) as unified memory.
Using qwen3.6 A3B Q8, I get to around ~200 tps using MTP and to ~150 tps without it!
And this still leaves plenty of VRAM for kv cache and context window...!
